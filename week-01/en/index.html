FOUNDATION · LLM

What is an LLM?

A language model that learns patterns from large amounts of text and generates what is likely to come next from the text provided so far.

SUMMARIZECLASSIFYEXPLAINDRAFT CODESUGGEST PLANS
mental-model.txt
Input  “If login repeatedly fails...”
  ↓ calculate patterns in context
Output “lock the account or require
       additional authentication...”
CAUTION

Being good at generating the next expression does not mean always knowing what is true in the real world.

HALLUCINATION

Hallucination: plausible but unsupported

Invented facts

Confidently names documents, options, or vulnerability IDs that do not exist.

Wrong connections

Links individually correct clues to the wrong cause or conclusion.

False completion

May claim “the test passed” even though nothing was executed.

A confident tone is not an accuracy score.

FALSE SUCCESS

A particularly dangerous sentence in security work

agent-run.log
[10:14:02] scanning target...
[10:14:03] no command executed
[10:14:04] no response captured

AI: “Vulnerability detection and verification are complete.”
Before accepting the conclusion, ask:
“What evidence proves completion?”

RISK

Tools expand capability and risk together. We therefore need permissions, input checks, execution limits, and a defined target scope.

MCP · SIMPLE VIEW

MCP is a common connection method for models and tools

AI appWhere a user provides a goal and sees the result
MCPDescribes available tools and call formats through a common protocol
External systemsFiles, databases, browsers, and internal APIs

Think of it like a connection standard such as USB. A connection alone does not give AI a goal or make it safe.

DO NOT CONFUSE

MCP is not an agent. It is one way to connect tools that an agent may use.

BEGINNER VIEW · BRAIN VS WORKER

LLM: a brain that produces an answer
Agent: a worker that performs the task

🧠
LLM

An expert advising at a desk

Reads text and produces the next output—an explanation, plan, or code. By default, it does not open files, click buttons, or run commands.

🧑‍🔧
AI AGENT

A worker moving with tools

Receives a goal, uses an LLM to choose the next action, runs approved tools, and chooses again from the result.

LLM: “Here is how to do it.”
Agent: “I will do it, inspect the result, and choose the next step.”
CAUTION

The LLM still handles reasoning and language inside an agent. The agent is the larger system that adds tools, state, and repeated execution.

SAME TASK · DIFFERENT BEHAVIOR

“Check the local login task”

TEXT IN → TEXT OUT

LLM: Send a login request with the class
account and look for the completion string.
Tell me the result and I will explain the next step.

It explains a method, but it did not send a request. This is not a verified completion result.

AGENT EXECUTION
GOAL → ACTION → EVIDENCE
1. Check approved target and done condition
2. Send request with class account
3. Observe status code and body
4. Pass completion-string candidate
5. Oracle checks the original response
6. Report status and evidence

It acts on and observes the environment with tools. The harness controls scope and verification.

AGENT LOOP

The core of an agent is an iteration loop

GoalThe task to finish
→
Plan & decideChoose the next action
→
Use a toolAct on the environment
→
Observe & reviseUse the result in the next loop

An agent is not something that creates a perfect plan at once. It adjusts its next action after seeing what actually happened.

CONCRETE LOOP

One RH-CASE-01 agent loop

🎯Check goal

Verify the required completion string with evidence.

→
💭Choose action

Decide to send an approved request with the class account.

→
🛠️Call tool

Use send_request once on the approved local target.

→
👀Observe

Read the status code and response body.

→
📝Update state

Save evidence; if insufficient, choose the next safe action.

REPEAT

The loop stops when the done condition is met, a limit is reached, or an action requires human approval.

STOP CONDITIONS

A good agent knows when to stop

SUCCESS

Evidence found

The done condition and supporting evidence are satisfied.

FAILURE

Error repeats

The same error remains after an allowed retry.

LIMIT

Budget reached

Time, tokens, or tool-call count reaches its limit.

APPROVAL

Ask a person

Stop before a risky or hard-to-reverse action.

Infinite loops and reckless guesses are design failures, not autonomy.

HARNESS

A harness is the agent's execution structure

A physical harness holds a person or machine safely while transferring force. In AI, a harness connects model capability to a goal, limits its scope, and checks the outcome.

THREE LAYERS

Model, agent, and harness as three layers

HarnessDesigns goal delivery, context selection, tool permissions, logging, verification, cost, and stop conditions
AgentReads the current state, chooses the next action, and tracks the goal

Industry sources draw the boundary between agent and harness differently. This course uses these three layers to keep responsibilities clear.

ROLE · DISPATCHER

The Dispatcher is the control-room coordinator

Like a taxi dispatcher matching a passenger request to a suitable driver, it reads a user request, divides the work, and routes it to the right agents.

InputUser goal, target scope, completion condition, current system state
DecisionWhich specialist is needed; parallel or sequential work; where to route a failure
OutputA structured AgentTask and execution order that each agent can understand
📨Intake

Check needed information instead of forwarding one large goal unchanged.

🚦Coordinate

Use progress and errors to decide the next call.

DO NOT CONFUSE

The Dispatcher does not perform every specialist analysis. Its main job is decomposition and coordination.

ROLE · TEAM A / TEAM B

A and B handle different vulnerability areas

TEAM A · AREA ONE

Complete one task end to end

Analyze input and design tool actions for the first area. Preserve execution results and original evidence to complete an L1 flow.

TEAM B · AREA TWO

Connect another area with the same contract

Handle a second area and return real input with evidence—or a clear failure log—from the same harness.

Task inputArea and allowed scope
→
DispatcherSelect A or B
→
SpecialistAction + observation + evidence

Each two-person team splits primary ownership between prompt/reasoning strategy and tool execution/failure logs. The partner must run or review the work with the same input.

ROLE · ORACLE

The Oracle is not an all-knowing AI; it is an evidence reviewer

1 · FORMAT

Is anything missing?

Check target, time, request, response, reproduction steps, and the claim.

2 · MEANING

Does evidence support the claim?

Do not turn an ordinary error log into a successful vulnerability claim.

3 · VERDICT

What is the status?

Return PASS, FAIL, UNKNOWN, or NOT_RUN with a reason.

verdict = { "status": "UNKNOWN", "reason": "No original response; reproduction cannot be checked", "required": ["response.txt", "reproduce.md"] }
IMPORTANT

An Oracle may also use an LLM and can be wrong. Use explicit verdict rules and original evidence; a person reviews high-risk final decisions.

ROLE · REPORTER

The Reporter turns results into a readable report

ReceivesWhat it doesWhat it must not do
A/B claims and original evidenceMerge matching facts and clearly separate conflictsFill gaps with plausible invented details
Oracle verdict and reasonMake verified, insufficient-evidence, and failed states visiblePresent insufficient evidence as success
Execution scope and logsOrganize reproduction, impact, limits, and next actionExpose sensitive values or unnecessary raw data

One teammate primarily owns Oracle rules and tests; the other owns Reporter logs and result tables. They cross-check verdict evidence and missing records.

SAFE SCOPE

Separate “we can” from “we may”

ALLOWED

Approved local training environment

  • A lab target we run ourselves
  • Addresses and functions named in class
  • Checks within the set calls, time, and tools
STOP

Stop outside the scope

  • Targets we do not own or have permission to test
  • Actions affecting real accounts, personal data, or services
  • Destructive or persistent actions not in the rules
PRINCIPLE

Safety is not a final warning. Target restrictions, tool permissions, stop conditions, and logs are built in from the start.

SECURITY TEASER

Vulnerabilities often begin with a broken assumption

Trusting input

Assuming user input is safe can create injection vulnerabilities.

Trusting access

Assuming that knowing an address grants permission can break access control.

Trusting output

Putting external data directly on a page may allow scripts to execute.

From next week, we will see how an agent observes these issues with tools and how a harness safely limits that work.

THREE SENTENCES

Leave today with these three sentences

  • An LLM generates output; an agent uses tools and repeatedly tracks a goal.
  • A harness connects the goal, context, tools, state, verification, and stop conditions.
  • Even with the same AI, the designed process and evidence change quality, safety, and cost.

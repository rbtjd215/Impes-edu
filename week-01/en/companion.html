Our semester case: RH-CASE-01

RH-CASE-01 is the name of the first shared RedHarness learning case. RH means RedHarness, CASE is the recurring scenario we build on throughout the semester, and 01 means the first case. We add one layer to the same case each week instead of switching to an unrelated problem.

Send a request with a class account to an authorized local login lab, confirm the required completion string in the actual response, and record the execution evidence and status.

We keep this educational case throughout the semester. In Weeks 1 and 2 we do not run Claude, APIs, code, or security tools. We study prepared requests, responses, and logs. From Week 3, we add baseline execution, the shared contract, real tool calls, verification, and integration one layer at a time.

The complete flow

Task input → Dispatcher → Specialist Module A or B
           → Approved tool → Oracle → Reporter
  • Task input: the authorized target, goal, limits, and completion condition.
  • Dispatcher: chooses the appropriate specialist.
  • Specialist A or B: chooses actions and uses approved tools within scope.
  • Oracle: checks whether original evidence supports the claim.
  • Reporter: records status, evidence, errors, and next action.
  • Shared harness: manages the contract, context, permissions, limits, state, verification, and logs.

Distinctions that matter

LLM vs. agent

LLM:   “Here is how you could do it.”
Agent: “I used an approved tool, observed the result,
        and selected the next step.”

An LLM may provide reasoning inside an agent. The agent is the larger system with tools, state, iteration, and stop conditions.

Prompt vs. context

A prompt is the current question or work instruction. Context is all information visible to the model for this decision. The prompt is part of the context, not a synonym for it.

Tool vs. MCP vs. agent

A tool performs an action. MCP is a connection method for tools and data. An agent combines goal, decisions, actions, observations, and stopping. Connecting a tool through MCP does not automatically create an agent.

Agent vs. harness

The agent decides the next action while tracking a goal. The harness controls available information and tools, limits, verification, and records. Sources may draw the boundary differently; this is the distinction used in our project.

A good prompt has four parts

PartQuestion
RoleWhat responsibility or perspective?
GoalWhat must be completed?
ConstraintsWhich scope, tools, actions, and formats are allowed or prohibited?
Done conditionWhat evidence proves completion?

Vague request: Check the login problem.

Improved: On the authorized local login lab, send a request using the class account. Find the required completion string in the response and return its exact location with the original response evidence. If it cannot be confirmed, do not guess PASS. Record evidence for UNKNOWN or FAIL instead.

Evidence and status

StatusMeaning
PASSExternal success evidence is present
FAILExecuted, with evidence of failure
UNKNOWNExecuted, but evidence is insufficient for a verdict
NOT_RUNNot actually executed

“The test passed” is only a sentence. A reliable result points to originals that another person can inspect. The following is a conceptual example, not a real Week 1 run:

Team roles

RoleMain responsibility
Integration · Education · DispatcherMaintains the shared structure, routes work, connects modules
Specialist ACompletes one area from input through verdict and log
Specialist BHandles another area and returns evidence or a clear failure log
OracleApplies verdict rules to claims and original evidence
ReporterProduces a reproducible record without inventing facts

Each two-person team splits primary ownership. One teammate focuses on prompt/reasoning or verdict rules; the other on tool execution/failure logs or reporting. A partner must run or review the work with the same input before the team calls it complete.

Safe scope

RedHarness may run only on a local educational lab we operate, against class-approved addresses, ports, and functions, and within the specified request, time, and tool limits.

It must not automatically run against school systems, public websites found through search, targets outside the allowlist, or systems involving real accounts, personal data, or destructive effects. External training sites—including PortSwigger Web Security Academy—are for human study only unless separate written authorization for automation is confirmed.

Publicly accessible does not mean authorized for automated testing.

When the team lead provides the static RH-CASE-01 request/response example, mark the apparent target, user-supplied values, result, and possible success evidence. Note two unfamiliar words. For “Check the login problem,” identify missing role, goal, constraints, and done condition. List your preferred modules or vulnerability areas and your preferred work style: prompt/reasoning, execution/logging, verification, or documentation/explanation.

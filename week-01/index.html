MCP · SIMPLE VIEW

MCP는 모델과 도구 사이의 공통 연결 방식

AI 앱사용자가 목표를 주고 결과를 보는 곳
MCP사용 가능한 도구와 호출 형식을 공통 규칙으로 전달
외부 기능파일, 데이터베이스, 브라우저, 내부 API

USB처럼 “연결 규격”에 가깝습니다. 연결되었다고 해서 AI가 목표를 세우거나 안전을 책임지는 것은 아닙니다.

헷갈림 주의

MCP = 에이전트가 아닙니다. MCP는 에이전트가 사용할 수 있는 도구 연결 방법 중 하나입니다.

🧠
LLM

책상에서 조언하는 전문가

받은 글을 읽고 설명, 계획, 코드 같은 다음 출력을 만듭니다. 기본 상태에서는 실제 파일을 열거나 버튼을 누르거나 명령을 실행하지 않습니다.

🧑‍🔧
AI AGENT

도구를 들고 움직이는 작업자

목표를 받은 뒤 LLM으로 다음 행동을 판단하고, 허용된 도구를 실행하며, 결과를 보고 다음 행동을 다시 선택합니다.

LLM: “이렇게 하면 됩니다.”
Agent: “직접 해보고 결과를 확인한 뒤 다음 단계로 가겠습니다.”
주의

에이전트 안에서도 생각과 언어 생성은 LLM이 담당합니다. 에이전트는 LLM을 포함하면서 도구·상태·반복 실행이 추가된 더 큰 시스템입니다.

ROLE · DISPATCHER

Dispatcher는 관제실의 배차 담당입니다

택시 관제실이 승객 요청을 보고 적절한 차량을 배정하듯, Dispatcher는 사용자 요청을 읽고 작업을 나누어 적절한 에이전트에 전달합니다.

입력사용자의 목표, 대상 범위, 완료 조건, 현재 시스템 상태
판단어떤 전문 역할이 필요한지, 병렬 또는 순차 실행인지, 실패 시 어디로 돌릴지
출력각 에이전트가 이해할 수 있는 구조화된 AgentTask와 실행 순서
📨요청 접수

큰 목표를 그대로 던지지 않고 필요한 정보를 확인합니다.

🚦흐름 조정

진행 상태와 오류를 보고 다음 호출을 결정합니다.

헷갈림 주의

Dispatcher가 모든 전문 분석을 직접 하는 것은 아닙니다. 작업을 분해하고 연결하는 책임이 핵심입니다.

ROLE · ORACLE

Oracle은 정답을 다 아는 AI가 아니라 증거 검수자

1 · 형식 검사

필수 자료가 있는가?

대상, 실행 시각, 요청·응답, 재현 절차와 주장 내용이 빠짐없이 제출되었는지 봅니다.

2 · 의미 검사

증거가 주장을 지지하는가?

로그에 단순 오류만 있는데 취약점 성공이라고 과장하지 않았는지 확인합니다.

3 · 판정

다음 상태는 무엇인가?

PASS, FAIL, UNKNOWN, NOT_RUN 중 하나와 이유를 Dispatcher에 돌려줍니다.

verdict = { "status": "UNKNOWN", "reason": "응답 원본이 없어 재현 여부를 확인할 수 없음", "required": ["response.txt", "reproduce.md"] }
중요

Oracle도 LLM을 사용할 수 있으므로 틀릴 수 있습니다. 그래서 판정 규칙과 원본 증거를 함께 사용하고, 위험한 최종 판단은 사람이 확인합니다.

ROLE · REPORTER

Reporter는 결과를 읽을 수 있는 보고서로 바꿉니다

입력으로 받는 것보고서에서 하는 일하면 안 되는 일
A·B의 주장과 원본 증거같은 내용은 합치고 충돌한 내용은 구분해 표시없는 사실을 자연스러운 문장으로 채우기
Oracle의 판정과 이유검증됨·증거 부족·실패 상태를 독자가 바로 보게 구성증거 부족을 성공처럼 표현하기
실행 범위와 로그재현 절차, 영향, 제한 사항, 다음 행동을 정리민감한 값이나 불필요한 원본을 그대로 공개하기

한 명은 Oracle 판정 규칙과 테스트, 다른 한 명은 Reporter 로그와 결과표를 주로 맡습니다. 두 사람은 판정 근거와 기록 누락을 서로 확인합니다.

학기 공통 사례: RH-CASE-01

허가된 로컬 로그인 실습 환경에 수업용 계정으로 요청을 보내고, 실제 응답에서 지정된 완료 문자열을 확인한 뒤 실행 증거와 상태를 기록합니다.

이번 학기에는 이 교육용 사례를 계속 이어서 사용합니다. 1·2주차에는 Claude, API, 코드, 보안 도구를 직접 실행하지 않고 준비된 요청·응답·로그를 읽습니다. 3주차부터 기준 실행, 공통 계약, 실제 도구 호출, 검증과 통합을 한 층씩 추가합니다.

전체 흐름

과제 입력 → Dispatcher → 전문 모듈 A 또는 B
          → 허용된 도구 → Oracle → Reporter
  • 과제 입력: 허가된 대상, 목표, 제한과 완료 조건을 정의합니다.
  • Dispatcher: 과제에 맞는 전문 모듈을 선택합니다.
  • 전문 모듈 A 또는 B: 허용 범위 안에서 행동을 고르고 승인된 도구를 사용합니다.
  • Oracle: 원본 증거가 주장을 뒷받침하는지 확인합니다.
  • Reporter: 상태, 증거, 오류와 다음 행동을 기록합니다.
  • 공통 하네스: 전체 흐름의 계약, 컨텍스트, 권한, 제한, 상태, 검증과 로그를 관리합니다.

핵심 용어

용어쉬운 정의RH-CASE-01에서의 예
LLM현재 입력을 바탕으로 답이나 행동 후보를 생성하는 언어 모델로그인 응답을 어떻게 살펴볼지 제안
프롬프트모델에 전달하는 질문 또는 작업 지시역할, 목표, 제약과 완료 조건을 정의
컨텍스트현재 판단에 사용할 수 있는 모든 정보대상, 이전 응답, 규칙과 남은 요청 횟수
도구모델의 텍스트 밖에서 실제 행동을 수행하는 기능허가된 로컬 실습 환경에 요청 전송
MCPAI 애플리케이션을 도구와 데이터에 연결하는 공통 프로토콜승인된 요청 도구를 연결하는 방법 중 하나
에이전트목표를 향해 행동을 선택하고 도구를 사용하며 결과를 관찰하는 시스템요청 전송, 응답 확인, 다음 안전한 행동 선택
하네스정보, 도구, 제한, 검증과 기록을 관리하는 실행 구조허용 대상, 요청 한도, Oracle 검사와 로그 강제
증거다른 사람이 직접 확인할 수 있는 원본 정보요청, 응답, 완료 문자열 위치와 재현 절차

헷갈리기 쉬운 차이

LLM과 에이전트

LLM:      “이렇게 하면 됩니다.”라고 방법을 제안합니다.
에이전트: 허용된 도구로 실행하고 결과를 관찰한 뒤
          다음 행동을 고릅니다.

LLM은 에이전트 안에서 판단을 돕는 구성요소가 될 수 있습니다. 에이전트는 여기에 도구, 상태, 반복과 중단 조건을 더한 더 큰 시스템입니다.

프롬프트와 컨텍스트

프롬프트는 현재 질문이나 작업 지시입니다. 컨텍스트는 이번 판단에서 모델이 볼 수 있는 모든 정보입니다. 프롬프트는 컨텍스트의 일부이지만 두 용어는 같은 뜻이 아닙니다.

도구, MCP, 에이전트

도구는 실제 행동을 수행합니다. MCP는 도구와 데이터를 연결하는 방식입니다. 에이전트는 목표, 판단, 행동, 관찰과 중단을 결합합니다. 도구를 MCP로 연결했다고 해서 자동으로 에이전트가 만들어지는 것은 아닙니다.

에이전트와 하네스

에이전트는 목표를 추적하며 다음 행동을 결정합니다. 하네스는 사용할 수 있는 정보와 도구, 실행 제한, 검증 방법과 기록 방식을 통제합니다. 자료마다 경계를 다르게 설명할 수 있지만 RedHarness에서는 팀 책임을 분명히 나누기 위해 이 구분을 사용합니다.

좋은 프롬프트의 네 요소

요소확인 질문
역할어떤 책임과 관점으로 작업해야 하는가?
목표무엇을 완료해야 하는가?
제약어떤 범위·도구·행동·형식을 허용하거나 금지하는가?
완료 조건어떤 증거가 있어야 완료라고 판단하는가?

모호한 요청: 로그인 문제를 확인해 줘.

개선한 요청: 허가된 로컬 로그인 실습 환경에 수업용 계정으로 요청을 보냅니다. 응답에서 지정된 완료 문자열을 찾고 원본 응답과 정확한 위치를 제시합니다. 문자열을 확인할 수 없다면 PASS를 추측하지 않고 UNKNOWN 또는 FAIL의 근거를 기록합니다.

증거와 상태

상태의미
PASS외부에서 확인 가능한 성공 증거가 있음
FAIL실행했고 실패를 보여 주는 증거가 있음
UNKNOWN실행했지만 판정할 증거가 부족함
NOT_RUN실제로 실행하지 않음

“테스트에 성공했습니다”는 문장일 뿐입니다. 신뢰할 수 있는 결과는 다른 사람이 확인할 수 있는 원본을 가리켜야 합니다. 다음은 개념 예시이며 실제 1주차 실행 결과가 아닙니다.

{
  "status": "PASS",
  "claim": "지정된 완료 문자열 확인",
  "evidence": ["request.txt", "response.txt", "reproduce.md"],
  "scope": "local-education-lab",
  "uncertainty": [],
  "next_action": "보고서 작성"
}

팀 역할

역할주요 책임
통합·교육·Dispatcher공통 구조 유지, 작업 분배, 모듈 연결
전문 모듈 A한 분야를 입력부터 판정과 로그까지 완주
전문 모듈 B다른 분야를 처리하고 증거 또는 명확한 실패 로그 반환
Oracle주장과 원본 증거에 판정 규칙 적용
Reporter없는 사실을 만들지 않고 재현 가능한 기록 작성

두 명으로 구성된 각 팀은 개인별 주 책임을 나눕니다. 한 명은 프롬프트·판단 전략 또는 판정 규칙을, 다른 한 명은 도구 실행·실패 로그 또는 결과 보고를 맡습니다. 같은 입력으로 짝이 실행하거나 검토해야 팀 작업을 완료로 인정합니다.

안전한 실행 범위

RedHarness는 우리가 운영하는 로컬 교육용 실습 환경에서, 수업이 명시적으로 허가한 주소·포트·기능과 정해진 요청 횟수·시간·도구 제한 안에서만 실행할 수 있습니다.

학교 시스템, 검색으로 찾은 공개 웹사이트, 허용 목록 밖의 대상, 실제 계정·개인정보·파괴적 결과가 관련된 시스템에는 자동 실행하면 안 됩니다. PortSwigger Web Security Academy를 포함한 외부 교육 사이트도 별도 서면 허가가 확인되기 전에는 사람의 학습 용도로만 사용합니다.

공개적으로 접속할 수 있다는 사실은 자동 테스트가 허가됐다는 뜻이 아닙니다.

2주차 준비

교수가 제공하는 RH-CASE-01 정적 요청·응답 예시에서 대상, 사용자가 전달한 값, 결과, 성공을 뒷받침할 수 있는 증거를 표시합니다. 이해하지 못한 단어 두 개를 적고, “로그인 문제를 확인해 줘”에서 빠진 역할·목표·제약·완료 조건을 찾습니다. 관심 있는 모듈 또는 취약점 분야 1·2순위와 선호 업무도 정합니다.

아직 모든 HTTP 용어를 알 필요는 없습니다. 2주차에는 같은 로그인 요청을 메서드, 주소, 헤더와 본문으로 나누어 살펴봅니다.

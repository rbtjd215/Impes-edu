Week 3 self-study guide · English · 2026-10-01

This guide is for members using Git and Codex together for the first time. Follow the setup steps once, then return to the sections you need. You do not need to memorize commands: send a request to Codex and check what it actually did. Work at your own pace; the workflow below applies when you work, not as a requirement to work every day.

Verify local checks, record upload, PR creation, merging into main, and actual feature completion separately. Use confirmed repository rules and the shared contract before relying on an earlier chat. 02 · Prepare GitHub, Git, and the repository

What to do

  1. Sign in to your own GitHub account and accept the repository invitation. Ask the coordinator if it is missing. You can read or clone this public repository without an invitation, but pushing your branch requires permission. Local preparation and read-only review can continue while invitations or authentication are unresolved; do not report uploading as complete. GitHub invitations
  2. Sign in to the Codex app with your own account. Git is the local tool for tracking changes; GitHub is the service for sharing them and creating PRs.
  3. Check whether Git and Python are installed. If not, tell Codex your operating system and ask for help. Follow any installation or sign-in steps that require your own action or approval. Get Git, Get Python
  4. Clone means downloading a working copy of a repository for the first time. Reuse an existing copy instead of cloning it again.
  5. Check the public name and email that your commits will use. Your own noreply address is available in GitHub Settings → Emails. Do not use another person's name or email. Commit email settings

04 · Start work with your team

What to do

State your team and task once in a new chat. If the team is clear, Codex starts with its guide without asking your name again. When resuming, include the branch, PR number, or task ID if you know it.

Before editing in a new chat, for a new goal, after changing branches, or when returning after an interruption, Codex checks the repository first. Confirmed rules, the shared contract, team guides, and your own handoff take priority over an earlier chat's memory.

  1. Check the folder, remote, branch, modified files, and untracked files.
  2. Run git fetch origin to obtain the latest remote state. Fetch does not merge changes into your working files.
  3. Compare remote main and your task branch and identify the applicable baseline. Continue your own unfinished changes; preserve and separate unrelated changes. Do not automatically pull, force-reset, or stash everything over existing changes.
  4. Find your task through its current branch → connected PR → task ID, then compare its handoff with the rules, contract, and team guide. Do not take the newest dated file from your team as your own handoff.
  5. Codex briefly shows latest-state check and base commit / goal / edit paths / tests / next action before working.

For continuous edits within the same goal and branch in the same chat, reuse the confirmed baseline. Recheck when the baseline or branch changes, when returning after an interruption, and immediately before uploading. The detailed procedure is 03_프로젝트/00_공통/작업시작_최신확인.md in the development repository.

A failed fetch, unresolved shared-baseline difference, or conflict puts new development on hold. Diagnosis, reading, plan comparison, and recording known facts from existing work can continue. Do not label an unchecked state as current or fully ready, or start new feature edits.

The shared contract's core meanings are below. Use PROJECT_SPEC.md for all fields and exception handling.

Result status Meaning
PASS Externally verifiable success evidence exists
FAIL Execution occurred and failure evidence exists
UNKNOWN Execution occurred, but evidence is insufficient to judge
NOT_RUN Execution did not occur

Dispatcher/A/B use NOT_RUN before execution and UNKNOWN after execution until Oracle judges. Oracle makes the final PASS/FAIL judgment once, and Reporter preserves its status and evidence. Teams can design domain-specific observation and judgment strategies. These execution-result statuses are distinct from test PASS/FAIL/SKIP in task records.

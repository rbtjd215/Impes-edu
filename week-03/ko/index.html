01 · 먼저 읽기: 내 파트와 이번 목표

할 일

현재 A파트는 인증우회, B파트는 XSS입니다. Oracle·Reporter는 판정과 기록을 함께 개발하는 하나의 2인 팀입니다. 팀별 책임은 개발 역할표에서 확인하고, 자신의 배정이 없거나 다르면 담당자에게 확인하세요.

팀 맡는 일
A · 인증우회 인증우회 모듈의 관찰·행동·근거 후보 구현
B · XSS XSS 모듈의 관찰·행동·근거 후보 구현
Oracle·Reporter Oracle은 최종 판정, Reporter는 그 상태·근거를 보존하며 기록

학생이 이용하는 공간은 두 곳입니다.

공간 쓰는 방법
Impes-edu 교육자료 읽기 자료·교육 안내 확인
Impes_RedHarness 공동 개발 규칙·코드·테스트·작업 기록·PR 관리

공동 개발 저장소와 브랜치·PR·커밋 이력은 공개입니다. 계획서나 구현물을 도입할 때도 공개할 내용부터 선별합니다.

처음 준비·환경 구축 후 작업·업로드는 다음 세 경로로 나눠 사용합니다. 처음에는 준비 경로를 읽고, 익숙해지면 작업 경로의 시작·마무리 문구만 사용하세요.

내가 하려는 일 읽는 순서
처음 준비하기 02 · 저장소 준비 → 03 · 프로젝트 연결 → 04 · 파트 시작 → 05 · 로컬 검사·첫 업로드. 로컬 필수 검사가 통과하면 업로드가 막혀도 06 · 계획서 읽기 검토는 진행할 수 있습니다.
환경 구축 후 작업하기 04 · 시작 또는 10 · 이어받기 → 07 · 작은 기능 → 08 · 채팅·하루 마무리. 같은 목표의 연속 요청마다 전체 준비를 반복하지 않습니다.
GitHub에 올리기 09 · 업로드·PR. 준비 기록의 첫 업로드는 05절에서 연습합니다. 기록 작성·로컬 테스트·push·PR·main 병합은 각각 다른 상태입니다. 작업 날짜와 빈도는 각 팀이 정합니다.

읽고 확인할 것

처음 준비하는 분은 02 · 저장소 준비 → 03 · 프로젝트 연결을 먼저 따라 하세요. 담당 파트의 시작 요청문은 04절에 있습니다. 이 01절에서는 내 팀과 전체 순서를 확인하면 됩니다.

정상 결과

A=인증우회·B=XSS·Oracle/Reporter 한 팀이라는 배정과 처음 준비할 순서를 이해합니다. 전체 하네스 완성이나 실제 취약점 공격 성공은 이번 환경 준비의 완료 조건이 아닙니다.

막혔을 때

자기 파트가 확실하지 않으면 담당자에게 배정을 확인하고, 프로젝트 연결 뒤 04절의 담당 미확인 안내를 따르세요. Codex는 필요한 배정만 확인합니다. 이름을 묻는 경우에도 안내를 위한 확인이며, 접근 권한이나 신원을 검증하는 절차가 아닙니다.

02 · GitHub·Git·개발 저장소 준비

할 일

  1. 본인 GitHub 계정으로 로그인하고 개발 저장소의 초대를 수락합니다. 초대를 받지 못했으면 담당자에게 요청하세요. 공개 저장소는 초대 없이 읽거나 clone할 수 있지만, 본인 브랜치를 업로드하려면 권한이 필요합니다. 초대·인증이 미완료여도 로컬 준비와 자료의 읽기 검토를 할 수 있으며, 업로드 완료로 표시하지 않습니다. GitHub 초대 안내
  2. Codex 앱에 본인 계정으로 로그인합니다. Git은 변경 이력을 관리하는 로컬 도구이고, GitHub는 이를 함께 보관하고 PR을 만드는 서비스입니다.
  3. 컴퓨터에 Git과 Python이 있는지 확인합니다. 없다면 Codex에게 운영체제를 알려 주고 설치를 요청할 수 있습니다. 설치·인증에 사람의 조작이나 권한 승인이 필요하면 안내에 따라 진행합니다. Git 다운로드, Python 다운로드
  4. 저장소를 처음 가져오는 작업을 clone이라고 합니다. 이미 가져온 폴더가 있다면 다시 복제하지 않고 그 폴더를 사용합니다.
  5. 커밋에 남길 공개 표시 이름과 이메일을 확인합니다. GitHub Settings → Emails에서 본인의 noreply 주소를 확인해 사용할 수 있습니다. 다른 사람의 이름·이메일을 대신 넣지 마세요. GitHub 커밋 이메일 안내

처음 준비하는 분: 폴더를 두 번 선택합니다

① 설치 도움을 받을 빈 준비 폴더를 만드세요. 예를 들어 컴퓨터에 RedHarness_준비 폴더를 만들고, Codex에서 프로젝트 추가로 이 폴더를 여세요. 폴더 여는 방법은 03절을 참고하세요.

② 아래 준비 요청문을 보내세요. Codex가 Git·Python 준비를 돕고, 준비 폴더 안에 개발 저장소를 내려받습니다. 내려받은 폴더 이름은 Impes_RedHarness입니다.

③ 복제가 끝나면 작업 폴더를 바꾸세요. Codex가 알려 준 경로에서 새로 생긴 Impes_RedHarness 폴더 자체를 선택해 프로젝트에 연결합니다. 준비 폴더는 설치 도움을 받는 출발점이고, 실제 개발은 저장소 폴더에서 진행합니다.

④ 저장소 프로젝트에서 새 채팅을 여세요. 03절의 경로 확인을 마친 뒤 04절로 넘어갑니다. Codex가 복제 완료를 알리면 다음에 선택할 정확한 저장소 경로를 확인하세요. 준비 폴더의 채팅에서 곧바로 개발을 시작하지 않습니다.

예를 들어 폴더가 다음처럼 생겼다면, 마지막에 선택할 곳은 아래의 **Impes_RedHarness**입니다.

RedHarness_준비/
└─ Impes_RedHarness/  ← 복제 후 Codex에 연결할 실제 작업 폴더
   ├─ AGENTS.md
   ├─ README.md
   └─ 03_프로젝트/

이미 복제한 저장소가 있다면 그 Impes_RedHarness 폴더를 바로 연결하고 03절에서 경로를 확인합니다.

정상 결과

저장소 폴더에 AGENTS.md, README.md, 03_프로젝트/가 있고 원격이 위 개발 저장소를 가리킵니다. Git·Python 버전과 루트·원격을 확인합니다. 작성자 설정 확인 상태는 별도로 표시하며, 본인 확인·설정은 업로드 전에 마칩니다. 작성자 값이 미확인이라는 이유로 로컬 검사·자료의 안전한 읽기 검토를 막지 않습니다. GitHub 로그인은 사람의 로그인 화면에서 진행합니다. 토큰·비밀번호·API 키·쿠키는 채팅이나 파일에 붙여 넣지 마세요.

막혔을 때

git 또는 python을 찾지 못하면 오류 메시지와 운영체제를 Codex에 알려 주세요. 설치 뒤 앱이나 터미널을 다시 열어야 경로가 반영될 수 있습니다. 403·권한 오류가 나면 본인 로그인·초대 수락·대상 저장소 권한을 확인합니다. 권한 설정을 임의로 바꾸거나 다른 계정의 자격 증명을 사용하지 않습니다.

03 · Codex에 로컬 프로젝트 연결

할 일

  1. Codex 화면의 Add new project 또는 프로젝트 추가 메뉴를 엽니다. Windows에서는 Ctrl+O로 폴더 선택을 열 수 있습니다. 버전에 따라 메뉴의 번역·위치는 달라질 수 있습니다. Windows 공식 안내
  2. 복제한 Impes_RedHarness 폴더 자체를 선택합니다. 상위 Projects 폴더나 03_프로젝트 하위 폴더를 선택하지 않습니다.
  3. 이미 프로젝트가 있으면 재사용합니다. 준비용 폴더를 열었다면 프로젝트 메뉴의 Edit project에서 복제본을 연결하고 기본 작업 폴더(Make primary)로 지정하거나, 복제본으로 새 프로젝트를 만듭니다. 새 채팅의 기본 Git 작업과 규칙 탐색은 기본 폴더를 사용합니다. 프로젝트 공식 안내
  4. 해당 프로젝트 안에서 새 Codex 채팅을 만들고 Local / This computer로 진행합니다. 이 안내는 자기 컴퓨터의 복제본을 기준으로 합니다. 실행 환경 공식 안내

Codex에 보낼 문구

이 채팅이 Impes_RedHarness 저장소 루트에서 실행되는지 확인해 주세요.
현재 경로, Git 브랜치와 원격, AGENTS.md·README.md·03_프로젝트
존재 여부를 짧게 보여 주세요. 기존 변경은 보존해 주세요.

정상 결과

Codex가 현재 작업 경로와 올바른 개발 원격을 보여 줍니다. 프로젝트를 연결했다고 GitHub에 파일이 자동 업로드되는 것은 아닙니다. 다른 컴퓨터에서 이어 작업할 때도 그 컴퓨터의 복제본과 Git 동기화 상태를 확인합니다.

막혔을 때

AGENTS.md나 Git 저장소를 찾지 못하면 프로젝트의 기본 폴더를 확인합니다. 잘못 선택했다면 복제본 루트로 다시 연결하고 새 채팅에서 경로를 재확인하세요. 같은 로컬 복제본에서 여러 채팅을 동시에 수정하면 변경이 섞일 수 있습니다. 본인의 미완료 작업을 이어갈 때는 그 브랜치와 폴더의 변경을 그대로 이어받습니다. 관련 없는 작업을 새로 시작하거나 같은 컴퓨터에서 동시 수정이 필요할 때만 Codex와 별도 worktree 사용을 정하세요. worktree를 만들면 실제 작업 경로와 브랜치를 다시 확인합니다.

04 · 내 파트로 작업 시작

할 일

새 채팅에서 담당 팀과 할 일을 한 번 말합니다. 팀이 명확하면 이름을 다시 확인하지 않고 해당 팀 안내로 시작합니다. 본인 작업을 이어갈 때는 알고 있는 브랜치·PR 번호 또는 작업 ID도 알려 주세요.

새 채팅·새 목표·브랜치 변경·중단 후 재진입에는 Codex가 파일 수정 전에 저장소부터 확인합니다. 이전 채팅의 기억보다 현재 저장소의 확정 규칙·공통 계약·팀 안내·본인 인계를 우선합니다.

  1. 현재 폴더·원격·브랜치와 기존 수정·미추적 파일을 확인합니다.
  2. git fetch origin으로 원격 최신 상태를 가져옵니다. fetch는 내 작업 파일을 자동으로 합치지 않습니다.
  3. 원격 main과 작업 브랜치의 차이·적용 기준을 확인합니다. 본인 미완료 변경은 이어받고, 무관한 변경은 보존·분리합니다. 기존 변경 위에서 자동 pull·강제 reset·일괄 stash를 하지 않습니다.
  4. 현재 브랜치에 연결된 인계 → 해당 PR → 작업 ID 순으로 본인 작업을 찾고 규칙·계약·팀 안내와 대조합니다. 같은 팀의 날짜가 가장 최신인 파일을 곧바로 본인 인계로 사용하지 않습니다.
  5. Codex가 최신 확인 결과·기준 커밋 / 목표 / 수정 경로 / 테스트 / 다음 행동을 짧게 보여 준 뒤 작업합니다.

fetch 실패·해결되지 않은 공통 기준 차이·충돌은 개발 착수 보류입니다. 원인 진단, 자료 읽기, 계획 비교와 기존 작업의 사실 정리는 할 수 있습니다. 확인이 안 된 상태를 최신·전체 준비 완료로 표시하거나 새 기능 수정을 시작하지 않습니다.

할 일

검사 명령은 개발 저장소 검증 안내를 기준으로 Codex가 읽고 실행합니다. 이 교육문서에 명령·코드를 별도로 고정하지 않습니다. 현재 제공되는 검사와 제안을 구분하고, 없는 검사를 실행했다고 쓰지 않습니다.

로컬 검사가 실패·SKIP이면 해당 항목·확인된 원인·다음 행동을 기록합니다. 로컬 테스트는 통과했지만 push가 실패하면 **“로컬 준비 확인 / 기록 업로드 미완료 / PR 미생성 또는 확인 상태”**로 구분합니다. 이때 계획서의 안전한 읽기 검토는 할 수 있지만 공동 업로드까지 완료됐다고 말하지 않습니다.

Dispatcher·A·B는 미실행에 NOT_RUN, 실행 후 Oracle 판단 전에는 UNKNOWN을 사용합니다. 최종 PASS/FAIL은 Oracle이 한 번 판정하고 Reporter는 그 상태·근거를 보존합니다. 팀은 분야별 관찰·판단 전략을 설계할 수 있습니다. 위 실행 결과 상태와 작업 기록의 테스트 PASS/FAIL/SKIP은 구분합니다.

09 · commit·push·PR와 수정자 확인

할 일

용어 실제로 완료되는 일
브랜치 이번 작업을 구분하는 Git 작업 줄기
commit 로컬 변경을 작성자·메시지·커밋 ID와 함께 저장

PR 브랜치의 변경·검증·설명을 보여 주고 통합을 제안
main 병합 PR 변경을 공동 기준 브랜치에 반영

push와 PR 생성만으로 main이 바뀌지는 않습니다. 팀이 정한 통합 방식에 따라 필요한 때 병합합니다. 공개할 코드·준비 기록·작업 기록만 선별하고, 자신과 무관한 기존 변경은 포함하지 않습니다. 업로드 전에 원격을 재확인하고 이번 diff·기록·PR 설명의 공개 범위를 검토합니다.

공개 가능한 이번 작업만

정상 결과

Codex가 포함할 파일 목록을 보여 주고, 해당 경로만 올립니다. GitHub에서 PR의 Files changed로 변경 내용을, Commits로 커밋 작성자와 커밋 ID를 볼 수 있습니다. 파일 화면의 History는 변경 커밋을, Blame은 줄별 마지막 변경 정보를 보여 줍니다. GitHub 파일 확인 안내

작업 기록에 별도의 수정자 이름이 없어도 커밋 작성자·committer와 PR 계정·커밋 ID를 함께 확인할 수 있습니다. 다만 Git 작성자 값은 사용자가 설정하는 정보입니다. 타인의 값으로 커밋하지 않고, Git 이력만으로 신원이나 접근 권한이 검증됐다고 설명하지 않습니다. GitHub 커밋 안내

충돌이나 무관한 변경을 발견하면 현재 상태를 Codex에게 확인시킵니다. git add ., 강제 push, git reset --hard로 일괄 처리하지 않습니다. 비밀값을 공개 이력에 올렸다면 단순 삭제만으로 이력에서 사라지지 않으므로 즉시 담당자에게 알리고 해당 비밀값을 폐기·재발급합니다.

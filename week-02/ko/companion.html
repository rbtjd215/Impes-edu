REDHARNESS · WEEK 02 · STUDENT COMPANION

기존 하네스로 배우는
RedHarness 설계

2주차 한국어 슬라이드를 혼자 복습하기 위한 설명 자료입니다. CAI와 PentestGPT의 한 실행을 다시 따라가고, 그 구조를 앞으로 만들 RedHarness의 역할과 자료에 연결합니다.

복습 목표이번 주의 범위 먼저 구분할 세 가지CAI의 한 실행 PentestGPT의 한 실행두 구조 비교 RedHarness에 연결하기미래 프로젝트 자료 AI 작업 요청스스로 확인하기

복습 후 이해해야 할 것

  1. AI의 제안, 프로그램의 처리, 도구의 실제 반환값을 구분합니다.
  2. CAI의 Agent, Runner, Tool, Handoff가 맡는 일을 순서대로 설명합니다.
  3. PentestGPT의 Supervisor, 일반 코드 검사, Executor, State, Trace를 구분합니다.
  4. 두 사례를 RedHarness의 Dispatcher, 전문 모듈, Oracle, Reporter에 연결합니다.
  5. 미래 프로젝트에서 시작 안내, 공통 계약, 모듈 자료, 테스트, 실행 기록이 필요한 이유를 설명합니다.
  6. 개발을 돕는 AI에게 기준·작업·범위·확인 방법을 포함해 요청합니다.

이번 주의 범위

2주차에는 공식 구조 문서와 수업용 가상 사례만 읽습니다. Claude, API, 코드, 보안 도구를 직접 실행하거나 설치하지 않습니다.

RH-CASE-01은 허가된 로컬 로그인 연습 문제를 나타내는 수업용 가상 사례 ID입니다. 아래 입력과 관찰은 CAI 또는 PentestGPT가 실제로 이 사례를 실행한 결과가 아닙니다.

목표 입력 → 행동 제안 → 허용 확인 → 도구 실행 → 실제 관찰 → 판정과 기록

이 순서를 따라가면 AI가 말한 것과 프로그램이 실제로 수행한 일을 구분할 수 있습니다.

먼저 구분할 세 가지

구분의미확인할 증거
AI의 제안다음에 무엇을 할지 제시한 답변 또는 도구 요청모델의 응답
프로그램의 처리요청 종류를 읽고 범위 검사, 도구 호출, 인계 등을 수행코드 경로와 실행 사건
실제 관찰도구나 환경이 돌려준 값원본 반환값과 기록

AI가 “상태를 확인했다”고 말해도 도구 반환값이 없다면 아직 실제 관찰을 확인한 것이 아닙니다. 설계 문서에서는 이 세 층을 섞지 않습니다.

CAI의 한 실행

목표와 관찰
  → Agent가 다음 행동을 제안
  → Runner가 응답 종류를 처리
  → Tool 호출 또는 다른 Agent로 Handoff
  → 도구 반환값 또는 새 담당의 답
  → 다음 판단 또는 종료
용어쉬운 뜻한 실행에서 하는 일
Agent판단 담당 AI목표와 지금까지의 관찰을 읽고 답변이나 도구 사용을 요청합니다.
Runner진행 프로그램Agent 응답이 종료, 도구 요청, 인계 중 무엇인지 읽고 다음 단계를 처리합니다.
Tool실제 기능Runner의 호출을 받아 허용된 기능을 수행하고 값을 반환합니다.
Handoff담당 인계 동작현재 Agent에서 다른 Agent로 담당과 필요한 입력을 넘깁니다.
Trace실행을 되짚는 기록 개념판단 요청, 도구 호출, 관찰을 시간순으로 확인하게 합니다.

Agent의 요청은 실행 결과가 아닙니다

Agent는 “연습 환경의 상태를 확인하자”라고 제안할 수 있습니다. 실제 행동은 Runner가 Tool을 호출할 때 일어납니다. Tool이 돌려준 값이 관찰이며, 이 값이 다음 Agent 판단의 입력으로 돌아갑니다.

Handoff는 파일이 아니라 동작입니다

Handoff가 일어나면 Runner는 현재 담당 Agent와 전달할 입력을 바꾸고 실행을 이어 갑니다. 목표, 필요한 관찰, 다음 질문처럼 인계에 필요한 정보를 전달할 수 있지만 수업의 세 항목이 CAI의 고정 파일 형식이라는 뜻은 아닙니다.

CAI의 Trace 설명에서 주의할 점

CAI 구조 문서는 tracing을 설계 축으로 소개하지만, 수업에서 확인한 보관본은 해당 구현을 진행 중이라고 표시합니다. 수업의 시간표 그림을 실제 CAI 로그 형식으로 해석하면 안 됩니다.

PentestGPT의 한 실행

저장된 State 읽기
  → Supervisor가 다음 작업 하나를 제안
  → 일반 코드가 작업과 허용 범위를 검사
  → Executor가 확인된 작업을 수행
  → 실제 관찰을 State와 Trace에 반영
  → 다음 작업 또는 종료
용어쉬운 뜻한 실행에서 하는 일
Supervisor작업 선택 담당 AI저장된 상황을 읽고 다음 작업 하나를 제안합니다.
일반 코드 검사정해진 규칙을 확인하는 프로그램대상 범위, 작업 유효성, 근거 출처, 상태 변경 조건을 검사합니다.
Executor작업 수행 담당 AI확인된 작업 하나를 받아 처리하고 실제 관찰을 남깁니다.
State다음 실행이 이어받을 저장 데이터현재 작업, 확정된 관찰, 남은 한도처럼 계속 진행할 정보를 담습니다.
Trace지나온 사건의 실행 기록선택, 호출, 반환, 오류가 일어난 순서를 되짚게 합니다.

명확한 규칙은 코드가 검사할 수 있습니다

허용 대상인지, 요청 한도를 넘었는지, 필수 입력이 있는지처럼 답이 명확한 조건은 새로운 AI 역할을 추가하지 않고 일반 코드로 검사할 수 있습니다. 실제 도구 권한은 격리된 실행 환경에서도 제한해야 합니다.

State와 Trace의 차이

State는 다음 실행이 어디서부터 이어갈지 알려 줍니다. Trace는 이전 실행에서 어떤 사건이 어떤 순서로 일어났는지 보여 줍니다.

중단 뒤 다시 시작하려면 마지막 작업, 실제 관찰, 남은 한도 같은 State가 필요합니다. 실패 원인을 검토하려면 작업 선택, 도구 호출, 반환값, 오류가 남은 Trace가 필요합니다.

CAI와 PentestGPT 비교

질문CAIPentestGPT 현재 구조
다음 일을 누가 고르나?Agent가 다음 행동을 제안Supervisor가 다음 작업 하나를 제안
실행 전후를 누가 처리하나?Runner가 도구 호출 또는 Handoff를 처리일반 코드가 작업을 검사하고 Executor가 처리
실제 행동은 어디서 일어나나?Runner가 Tool을 호출할 때확인된 작업을 Executor와 도구가 처리할 때
무엇을 남기나?도구 반환값을 다음 판단에 전달. Trace 구현 상태는 별도 확인 필요이어받을 State와 되짚을 Trace를 구분

두 구조 중 하나를 그대로 복제하는 것이 이번 수업의 목표는 아닙니다. 책임이 어디에 놓이는지 읽고 RedHarness에 필요한 책임과 자료를 질문하는 것이 목표입니다.

RedHarness에 연결하기

RH-CASE-01 입력
  → Dispatcher
  → 전문 모듈 A 또는 B 하나 선택
  → Oracle
  → Reporter
  • Dispatcher: 사례 입력을 읽고 전문 A 또는 B 중 알맞은 담당을 선택합니다.
  • 전문 모듈 A/B: 관찰을 해석하고 다음 행동 후보를 만들며, 허용된 도구를 통해 실제 관찰을 얻습니다.
  • Oracle: 주장과 원본 관찰을 비교해 근거가 충분한지 판정합니다.
  • Reporter: 상태, 근거, 오류와 다음 행동을 재현 가능한 형태로 기록합니다.

처음에는 입력 분야에 따라 전문 A 또는 B 하나를 선택합니다. 두 모듈의 병렬 실행은 공통 입출력과 결과 병합 기준을 정한 뒤 검토합니다. 네 가지 책임이 각각 별도 AI Agent여야 한다는 뜻도 아닙니다.

전문 모듈 안의 반복

공통 입력
  → AI가 다음 행동 후보 제안
  → 일반 코드가 범위와 한도 검사
  → 허용된 Tool 실행
  → 실제 관찰 저장
  → 근거가 부족하면 반복, 충분하면 Oracle로 전달

관찰 해석과 다음 행동 제안은 AI가 맡을 후보이고, 범위·한도 검사와 도구 호출은 일반 코드가 관리할 수 있습니다. 반복 횟수와 종료 조건은 3주차 이후 공통 계약과 mock으로 확인합니다.

역할 수와 비용

Agent를 추가하면 전문 역할을 나눌 수 있지만 호출 횟수와 인계할 정보도 늘 수 있습니다. 같은 입력으로 성공 근거, 토큰, 도구 호출 횟수, 실행 시간과 실패 기록을 함께 비교해야 합니다. 2주차에는 사람의 담당 파트만 정하며 AI Agent 수는 확정하지 않습니다.

AGENTS.md와 prompt.md

파일 예시읽는 주체용도
AGENTS.md프로젝트 개발을 돕는 코딩 AI수정 범위, 공통 문서, 검증과 기록 방법을 안내합니다.

두 파일은 읽는 주체와 사용 시점이 다릅니다. AI를 사용하지 않는 모듈에는 실행용 prompt가 필요하지 않을 수 있고, 실제 파일명도 팀의 선택에 따라 달라질 수 있습니다.

tests와 runs

  • Mock은 실제 도구 대신 미리 정한 반환값으로 흐름을 확인하는 시험 방법입니다.
  • tests/는 고정 입력과 mock을 사용해 계약과 동작을 반복 확인할 자리입니다.
  • runs/는 실행 사건, 관찰, 오류를 남길 자리입니다. 비밀값을 제거하고 Git에 포함할 범위는 별도로 정합니다.

과제와 3주차 준비

2주차 첫 과제는 수업에서 배정받은 담당 파트의 하네스 구성을 한 페이지로 제안하는 활동입니다. 구현이나 설치, AI Agent 수 확정은 요구하지 않습니다.

  1. 담당 파트의 책임
  2. RH-CASE-01에서 받을 입력과 돌려줄 결과
  3. AI 판단이 필요한 후보와 코드가 맡을 규칙·종료 조건
  4. CAI 또는 PentestGPT에서 참고할 구조와 필요한 자료
  5. 3주차 mock에서 확인할 항목과 아직 모르는 점

정확한 공식 읽을 위치, 제출 위치와 마감은 검수된 과제지에서 안내합니다. 과제지는 아직 배포되지 않았습니다. 개인의 제안은 3주차 공통 계약을 검토하기 위한 질문이며, 제출만으로 팀의 최종 설계가 확정되지는 않습니다.

지난주 개념 연결 W02-S02

하네스의 한 작업에는 어떤 단계가 있나?

하네스(Harness)는 파일이나 AI 역할의 이름이 아니라, AI의 제안을 프로그램의 도구 호출·결과 확인·기록으로 연결하는 실행 구조입니다. 이 순서를 따라가면 AI가 말한 것과 실제로 일어난 일을 구분할 수 있습니다.

목표 입력무엇을 할까?
→
행동 선택AI의 제안
→
도구 실행프로그램의 행동
→
관찰실제 반환값
→
판단·기록근거 남기기

예: AI가 “조회해 줘”라고 말해도 도구 반환값이 없으면 아직 관찰한 것이 아닙니다.

CAI · 전체 실행 흐름 W02-S04

CAI에서는 요청을 처리한 뒤 결과를 다시 전달한다

먼저 판단 담당 AI가 다음 행동을 제안합니다. 진행 프로그램은 응답에 따라 도구를 호출하거나 다른 AI에게 일을 넘깁니다. 도구 결과나 새 담당의 답은 다음 판단에 사용됩니다. CAI에서는 이를 Agent, Runner, Tool, Handoff라고 부릅니다.

① 다음 행동 제안Agent · AI가 판단
→
② 응답 처리Runner · 프로그램이 진행
→
③ 도구 실행 / 담당 인계Tool 호출 또는 Handoff
→
④ 결과 전달도구 반환값 또는 새 담당의 답
반복 또는 종료③에서는 도구 실행과 담당 인계 중 응답에 맞는 길로 갑니다. 결과로 다음 판단을 하거나 종료합니다.

공식 자료: CAI architecture · Running agents (archive, 2026-09-21 확인). 보관된 공식 자료를 구조 학습에 사용하며 코드 재사용 여부는 아직 정하지 않았습니다.

CAI 전체 흐름 · ① 다음 행동 제안 W02-S05

판단 담당 Agent는 목표와 관찰에서 다음 요청을 만든다

Agent(에이전트)는 목표와 지금까지의 관찰을 읽고 답을 만들거나 도구 사용을 요청하는 AI 역할입니다. 사람 팀원의 담당과는 다릅니다. RH-CASE-01에서는 “무엇을 더 확인할까?”를 제안할 수 있지만, 요청 자체가 도구 실행을 뜻하지는 않습니다.

목표와 관찰허가된 연습 문제의 현재 정보
→
다음 행동 판단CAI 이름: Agent
→
답변 또는 도구 요청아직 도구를 실행한 상태가 아님

핵심: AI의 제안과 프로그램의 실제 행동은 따로 확인합니다.

출처: CAI architecture · Agent

CAI 전체 흐름 · ② 응답 처리 W02-S06

진행 프로그램 Runner는 응답에 따라 다음 단계를 처리한다

Runner는 AI Agent가 아니라 실행 순서를 관리하는 프로그램 코드입니다. Agent의 응답이 종료·도구 요청·인계 중 무엇인지 보고, 도구 결과를 다음 입력에 붙이거나 담당 Agent를 바꿉니다.

AI의 응답답변·도구 요청·인계 요청
→
진행 프로그램Runner · 응답 종류를 읽음
→
종료·도구·인계응답에 맞는 한 단계 처리
반복도구 결과나 새 담당 Agent의 답이 들어오면 다음 판단을 이어갑니다.

출처: CAI · Running agents, Agent loop

CAI 전체 흐름 · ③ 도구 실행 W02-S07

도구 Tool은 요청받은 기능을 실제로 수행한다

Tool(도구)은 별도의 AI 역할이 아니라 Agent의 요청에 따라 프로그램이 실행하는 기능입니다. 수업용 사례에서는 허용된 연습 환경의 상태 조회를 예로 듭니다. 반환값이 관찰이며 AI가 “완료했다”고 쓴 문장과 구별합니다.

Agent의 요청“연습 환경의 상태를 확인해 줘”
→
Runner의 Tool 호출허용된 기능을 프로그램이 실행
→
반환값“상태: 확인 필요” 같은 관찰
함께 확인: 실제 행동은 어느 칸에서 일어날까요? 정리: Runner가 Tool을 호출할 때 일어납니다.

출처: CAI · Agent loop. 반환값은 수업용 가상 예시입니다.

CAI 전체 흐름 · ③ 담당 인계 W02-S08

담당 인계 Handoff가 일어나면 다음 AI가 이어받는다

Handoff(인계)는 기록 파일이 아니라, 현재 Agent가 다른 Agent에게 일을 넘기는 동작입니다. CAI의 Runner는 인계가 나오면 담당 Agent와 전달할 입력을 바꿔 실행을 이어갑니다.

현재 담당관찰을 읽고 전문 역할이 필요하다고 판단
→
넘길 정보목표 · 필요한 관찰 · 다음 질문
→
다음 담당넘겨받은 정보로 판단을 이어감

가운데 상자는 수업용 설명 그림이며 실제 파일이 아닙니다. CAI가 이 세 항목을 고정 형식으로 요구한다는 뜻도 아닙니다.

출처: CAI · Agent loop과 handoff input filter

CAI 전체 흐름 · 단계별 기록 개념 W02-S09

실행 기록 Trace로 일어난 일을 순서대로 되짚는다

Trace(실행 흔적)는 판단 요청, 도구 호출, 관찰을 시간순으로 되짚는 기록 개념입니다. ‘Trace’라는 이름의 특정 파일을 뜻하지 않습니다. 최종 답 한 줄만으로는 과정과 근거를 확인하기 어렵습니다.

RH-CASE-01 · 수업용 가상 시간표 01 Agent가 상태 확인을 요청 02 Runner가 허용된 Tool을 호출 03 Tool 반환값을 관찰로 기록 04 Agent가 관찰을 바탕으로 다음 답변

CAI의 구조 문서는 tracing을 설계 축으로 소개하지만, 해당 항목의 구현은 진행 중이라고 표시합니다. 위 시간표는 실제 CAI 로그가 아닙니다.

출처: CAI architecture · Tracing

CAI 전체 흐름 · ④ 결과와 반복 W02-S10

도구 결과는 Agent의 다음 입력으로 돌아간다

Agent가 다음 행동을 고르면 Runner는 종료·도구 호출·인계 중 알맞은 단계를 처리합니다. 도구 결과는 다시 Agent의 입력이 됩니다. 이 루프를 따라가면 누가 판단하고 누가 실행했는지 보입니다.

다음 행동 제안판단 담당 · Agent
→
응답 처리진행 프로그램 · Runner
→
도구 실행 / 담당 인계Tool 호출 또는 Handoff
→
처리 결과관찰 또는 새 담당의 답
되돌아감도구의 관찰은 판단 담당에게, 인계한 내용은 새 담당에게 전달합니다.
함께 확인: 관찰은 어느 단계로 돌아갈까요? 정리: Agent의 다음 판단으로 돌아갑니다.

PentestGPT · 전체 실행 흐름 W02-S11

PentestGPT에서는 한 작업을 선택·검사·실행·저장한다

저장된 상황을 읽고 선택 담당 AI가 다음 작업 하나를 고릅니다. 코드 확인을 거쳐 수행 담당 AI가 처리하고, 관찰을 저장해 다음 작업으로 이어 갑니다. PentestGPT는 두 역할을 Supervisor와 Executor라고 부릅니다.

① 현재 상황 읽기저장 상태 · State

→

→
⑤ 관찰·저장결과와 실행 기록 · Trace

PentestGPT 전체 흐름 · 담당 구분 W02-S12

작업 제안과 실제 수행 사이에 코드 검사가 있다

작업 선택 담당(Supervisor)는 현재 상태를 바탕으로 할 일을 제안합니다. 일반 코드가 작업과 허용 범위를 확인합니다. 작업 수행 담당(Executor)는 전달받은 작업을 수행하고 실제 결과를 돌려줍니다.

PentestGPT 전체 흐름 · ② 작업 선택 W02-S13

작업 선택 담당은 다음에 할 일 하나를 제안한다

작업 선택 담당은 저장된 현재 상황을 읽고 다음 작업 하나를 제안하는 AI입니다. PentestGPT에서는 이 역할을 Supervisor라고 부릅니다. RH-CASE-01 예시에서 “연습 환경 상태 확인”을 고를 수 있지만, 이 제안은 실행 결과가 아닙니다. 우리도 같은 이름이나 별도 AI를 반드시 쓸 필요는 없습니다.

PentestGPT 전체 흐름 · ③ 코드 검사 W02-S14

일반 코드는 작업과 허용 범위를 검사한다

여기의 일반 코드는 새로운 AI Agent가 아니라 정해진 조건을 검사하는 프로그램입니다. PentestGPT에서는 대상 범위, 작업의 유효성, 근거 출처, 상태 변경을 코드가 관리합니다. 실제 도구 권한은 격리된 배포 환경을 경계로 삼습니다.

PentestGPT 전체 흐름 · ④ 작업 수행 W02-S15

작업 수행 담당은 확인된 일 하나를 처리한다

작업 수행 담당은 확인된 작업 하나를 받아 처리하는 AI입니다. PentestGPT에서는 이 역할을 Executor라고 부릅니다. AI가 “수행했다”고 적은 문장과 도구가 남긴 실제 관찰은 구별해야 합니다. 다음 판단은 관찰과 저장된 상태를 바탕으로 이어집니다.

PentestGPT 전체 흐름 · ①·⑤ 상태와 기록 W02-S16

저장 상태는 이어받고 실행 기록은 되짚는다

State는 이어받을 저장 데이터이고, Trace는 지나온 사건의 실행 기록입니다. PentestGPT에서는 SQLite 데이터베이스에 저장된 상태가 기준이며, 실행 사건은 별도 기록으로 남습니다. 용어만으로 특정 파일명을 뜻하지는 않습니다.

중단 뒤에는 저장된 상태에서 작업을 이어 간다

CAI와 PentestGPT 비교 W02-S18

두 사례는 판단·실행·기록을 어디에 맡겼나?

두 사례 모두 AI의 제안, 실제 실행, 결과 확인을 구분합니다. CAI에서는 Runner의 도구 호출과 인계를, PentestGPT에서는 작업 선택·코드 검사·수행·상태 저장을 확인할 수 있습니다.

한 작업에서 묻는 것CAIPentestGPT 현재 구조

실행 전후를 누가 처리하나?진행 프로그램(Runner)이 도구 호출·인계 처리일반 코드가 범위를 확인하고 수행 담당(Executor)이 작업
무엇을 남기나?도구 반환값으로 다음 판단. Trace는 구현 상태 확인 필요저장 상태(State)와 실행 기록(Trace)을 구분

RedHarness · 앞으로 만들 흐름 W02-S19

입력에 맞는 전문 A 또는 B를 거쳐 판정·기록한다

담당 선택(Dispatcher)이 사례에 맞는 전문 모듈로 보냅니다. 전문 A 또는 B가 관찰과 행동을 맡고, 근거 판정(Oracle)과 결과 기록(Reporter)으로 이어집니다.

① 사례 입력RH-CASE-01 자료
→
② 담당 선택Dispatcher
→
③ 전문 AA 분야 관찰·행동
③ 전문 BB 분야 관찰·행동
→
④ 근거 판정Oracle
→
⑤ 결과 기록Reporter

처음에는 입력 분야에 따라 A 또는 B 하나를 선택하는 구조로 시작합니다. 두 모듈을 함께 실행하는 병렬 방식은 공통 입출력과 결과 병합 기준을 정한 뒤 검토합니다. 이 다섯 책임이 곧 다섯 AI Agent를 뜻하지 않습니다.

RedHarness 전체 흐름 · ③ 전문 모듈 내부 W02-S20

전문 모듈은 판단·검사·도구 실행을 반복한다

전문 A와 B는 분야가 달라도 같은 기본 흐름을 사용할 수 있습니다. AI는 관찰을 해석해 다음 행동을 제안하고, 일반 코드는 범위와 한도를 확인한 뒤 도구를 실행합니다.

공통 입력사례·허용 범위·현재 관찰
→
다음 행동 제안AI 판단 후보
→
범위·한도 검사일반 코드
→
도구 실행허용된 기능 호출
→
실제 관찰 저장결과와 근거
근거가 부족하면 반복새 관찰을 다음 판단에 전달합니다. 충분하면 결과와 근거를 Oracle에 넘깁니다.
함께 확인: AI가 맡을 후보와 일반 코드가 맡을 부분은 어디인가요? 정리: 관찰 해석과 행동 제안은 AI 후보이고, 범위·한도 검사와 도구 호출은 코드가 관리합니다.

반복 횟수와 종료 조건은 3주차 이후 공통 계약과 mock으로 확인할 설계 가설입니다.

수업 중 담당 배정 · 약 5분 W02-S22

제안 구조 · 아직 미확정 W02-S24

이것은 앞으로 만들 개발 프로젝트의 제안 구조입니다. 이름 끝의 /는 폴더, .md·.json은 자료 파일을 뜻합니다. 실제 이름과 배치는 3주차에 공통 계약과 기술을 정하며 확정합니다.

redharness/
├─ README.md             시작·실행 안내
├─ AGENTS.md             개발 보조 AI 규칙(선택)
├─ .gitignore / .env.example
├─ docs/
│  ├─ PROJECT_SPEC.md      공통 계약
│  └─ THIRD_PARTY.md       외부 자료 출처
├─ modules/
│  ├─ dispatcher/
│  ├─ specialist_a/
│  │  ├─ README.md
│  │  ├─ MODULE_SPEC.md
│  │  ├─ sample_io.json
│  │  └─ prompt.md         모델 사용 시
│  ├─ specialist_b/
│  ├─ oracle/
│  └─ reporter/
├─ tests/                 고정 입력·mock
└─ runs/                  실행 결과·오류

루트는 새 팀원의 출발점입니다.

docs에는 모든 모듈이 같이 쓰는 약속을 둡니다.

modules는 담당별 책임과 예시의 자리입니다.

tests는 같은 입력으로 확인하는 자리입니다.

runs는 실행 결과를 남기는 자리이며 생성 로그는 원칙적으로 Git에서 제외합니다.

이름이 비슷한 두 지시 파일 W02-S26

AGENTS.md와 실행용 prompt는 읽는 주체가 다르다

AGENTS.md와 prompt.md는 둘 다 문서 파일의 예지만 읽는 주체가 다릅니다. AGENTS.md는 개발을 돕는 코딩 AI의 작업 규칙, 모듈의 prompt.md는 RedHarness 실행 중 모델에게 줄 목표와 입출력 지시를 담을 수 있습니다.

개발할 때 읽는 문서

AGENTS.md → 코딩 AI

“담당 모듈만 수정하고, 공통 계약을 읽은 뒤 확인 결과를 남겨라.”

하네스 실행 중 읽는 문서

prompt.md → 모듈의 모델

두 문구는 수업용 예시입니다. AGENTS.md라는 이름은 선택할 수 있는 방식이며 AI를 쓰지 않는 모듈에는 실행용 prompt가 필요하지 않을 수 있습니다.
